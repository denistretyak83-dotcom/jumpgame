# План действий (Action Plan) — «Jump & Reach the Flag»

Согласованный план для команды, построенный на стыке двух документов:

- **ARCHITECTURE_PLAN.md** (v2.0) — обновлённый архитектурный план (принципы, дорожная карта раздел 3, план рефакторинга раздел 4, конвенции раздел 5, риски раздел 7, рекомендуемый порядок).
- **AUDIT_REPORT.md** — аудит фактического кода из `jumpgame.zip` (структура, SOLID/MVC/OCP, риски, мусорные модули, оценка ≈6,5/10).

Plannerator-документ практичный, готов к исполнению командой. Каждый пункт привязан к разделам плана (X.Y) и конкретным файлам кода.

## 1. Цель и принципы

**Цель плана** — довести проект до состояния, соответствующего заявленным архитектурным принципам (DI без глобалов, MVC с DTO, OCP-регистрация, EventBus, Data-Driven уровни) и зафиксированному в плане уровню зрелости, двигаясь малыми проверяемыми шагами.

**Ключевое ограничение** (из плана, «1. Обзор»): **_игра работает и должна продолжать работать_**. Все правки — поэтапно, под покрытием юнит-тестов, без рискованных одномоментных изменений.

**Принципы (из раздела 5 плана):**

- **Поэтапность** — никакой одновременной больсой работы; каждое изменение в маленьком PR.
- **Под тестами** — рефакторинг только после/вместе с покрытием (4.4, конвенция «Тестирование»).
- **OCP-регистрация** — новый тип объекта/вью/поведения/состояния = регистрация, не модификация существующих классов (5).
- **Без глобалов/синглтонов** — DI через конструкторы, точка создания `main.py` (5).
- **EventBus через GameEvents.*** — события только через константы (7/5).
- **Именование** — зарезервированные properties Entity, `bound_*`/`patrol_*`, snake_case (5).

**Исходная точка (из аудита):** код в целом соответствует осям DI/MVC-Observer/OCP, но есть мусорные файлы, ноль тестов/CI, God-Object Game, незакрытый global `settings`-импорт и 4 подтверждённых риска. Фактическая оценка ≈6,5/10 против заявленных 8/10.

## 4. Порядок и зависимости

```
Фаза 0 (санитизация) ──┐
                     ┌──▼──────┐
Фаза 1 (инструменты) ─┤         │
                     └──▼──────┐
Фаза 2 (тестовый фундамент) ──┼──►  Фаза 3 (декомпозиция Game) ──►  Фаза 4 (геометрия/pygame.Rect)
        ▲                      │                                            │
        └── помимо, можно      └►  Фаза 5 (Data-Driven в2/в3/в4, C, I1) ────┴──►  Фаза 6 (фичи B,D,E,F)
                                   (частично параллельно с 3/4, но аккуратно)
```

**Ключевые зависимости:**

- **Фаза 0 предшествует всем** — иначе мины импорта ломают CI/тесты на старте.
- **Фаза 1 предшествует фазе 2 и далее** — нужен CI, чтобы тесты работали автоматически.
- **Фаза 2 → Фаза 3/4:** «без тестов нельзя декомпозицию» — тесты T2 (CollisionSystem) и T5 (Game) обязательны **до** выноса коллизий и до отказа от `pygame.Rect`.
- **Фаза 3 предшествует фазе 4** — проще менять геометрию, когда правила уже вынесены из Game.
- **Фаза 5 (I1) предшествует 3.E (редактор)** — нужна стабильная схема.
- **Фаза 6 F (разрушаемые блоки) зависит от появления атаки героя** (которого пока нет; возможно в B/другой фиче).
- **H1 (производительность) — P0 и можно рано** (параллельно с фазой 2): измеряет фреймрейт, чтобы не допустить регрессий при рефакторингах.

**Можно параллелить:**

- Фаза 0 с Фазой 1 (инструменты чисто, не конфликтуют с удалением мёртвых файлов).
- H1 (аудит фреймрейта) с Фазами 0–2.
- Частично Между фазами 3/4 и 5 (функциональные вью/поведения врагов не должны пересекаться с правилами коллизий — аккуратно через отдельные PR).
- Фаза 5 (A-в2/в3) и Фаза 6 (B/D) — после стабилизации схемы (I1).
