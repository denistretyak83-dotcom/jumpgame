## 1. Обзор

**Цель документа** — зафиксировать текущее состояние архитектуры проекта, закрепить принципы и конвенции, а также дать практичную, приоритизированную дорожную карту расширения игры. Документ адресован разработчикам и должен выполнять роль единого источника истины по архитектурным решениям.

**Краткое описание проекта**: «Jump & Reach the Flag» — 2D-платформер, в котором игрок прыгает по платформам, собирает монеты, избегает врагов и достигает флага. Проект прошёл масштабный рефакторинг и построен на принципах SOLID, MVC, DI (инъекция зависимостей), EventBus (Observer) и Data-Driven уровней из JSON.

**Ключевое ограничение:** игра работает и должна продолжать работать. Все правки выполняются поэтапно, под покрытием юнит-тестов, без рискованных одномоментных изменений.

## 2. Текущее состояние архитектуры

### 2.1 Слои

| Слой | Модули | Ответственность |
|---|---|---|
| **Модели** | `models/*` | игровая логика, физика, коллизии, состояния, поведение |
| **Виды** | `views/*` | отрисовка: рендер, анимации, HUD, фон, тайлы |
| **Контроллеры** | `controllers/*` | ввод игрока, преобразование в намерения |
| **Ядро** | `core/*` | оркестрация, события, конфиг, логирование, камера, сервисы, состояние |
| **Уровни** | `levels/*` | загрузка/построение уровней из JSON |
| **Аудио** | `audio/*` | звуки и музыка через EventBus |
| **Точка входа** | `main.py` | сборка приложения через DI |

### 2.2 Ключевые архитектурные решения

1. **DI (полный)** — настройки (Settings) и логгер (GameLogger) инжектируются через конструкторы. Глобальных settings/logger НЕТ, точка создания — main.py (Settings() -> GameLogger(config=logging) -> Game(config, logger)).
2. **MVC с DTO** — модель отдаёт чистые данные (ModelVisualData) без pygame; View (Renderer/SpriteCache/CharacterView) превращает их в кадры через цепочку get_visual_data() -> build_state() -> render(); Controller (PlayerController/EventBus) — единственный читает ввод и переводит события.
3. **EventBus (Observer)** — токенизированная подписка с изоляцией ошибок; все события — константы GameEvents.*.
4. **Композиция и протоколы вместо наследования** — DeathBehavior/RespawnBehavior (ABC), AnimatableCollidable (Protocol), PhysicsComponent композиция внутри BaseCharacter.
5. **Factory registry (OCP)** — WorldFactory с register()/create()/entity_factories(); новые объекты добавляются register() без изменения LevelManager.
6. **State machine игрока** — PlayerStateMachine + состояния Idle/Run/Jump/Fall.
7. **Ротация логов** — LogConfig (max_age_days, max_files), выполняется при старте.
8. **Data-Driven враги (в1)** — персональные width/height/speed/type из данных уровня с fallback на config.enemy.

### 2.3 Принципы и конвенции имён

КРИТИЧНАЯ КОНВЕНЦИЯ (из аудита properties): x, y, width, height, left, top, right, bottom, centerx, centery ЗАРЕЗЕРВИРОВАНЫ за свойствами Entity (делегируют во внутренний pygame.Rect). Запрещено использовать их как собственные поля класса-наследника с другой семантикой. Границы зон/патруля называть bound_left/bound_right (или patrol_*). Исправлено в Enemy (bound_left/bound_right).

Прочие конвенции:

- Физика пишет в entity.rect.*; сущность, владеющая собственным float-источником (Enemy._float_x), не должна одновременно попадать в цикл физики.
- Модель не знает о pygame в своих return-значениях (только ModelVisualData).
- View не читает модель напрямую — только через параметры/DTO.

## 3. Приоритизированная дорожная карта расширения

Приоритеты: P0 — высокий, P1 — средний, P2 — низкий/идея.

### A. Враги: типы и размеры (P0 — уже начат)

- в1 (сделано) — Enemy принимает enemy_data (width/height/speed/type), fallback на config.enemy. SpriteCache.enemy_view() пока единая под config.enemy.
- в2 (высокий) — поведение по типу: ввести EnemyBehavior Protocol (аналогично DeathBehavior), регистрировать поведения (walker/chaser/turret), ветвление по enemy_type. OCP: новый тип = новая регистрация поведения, без правки Enemy.update.
- в3 (средний) — анимации/View под тип и размер: SpriteCache.build_enemy_view_for(size/type), Renderer.view_registry выбирает вью по типу врага.
- в4 (средний) — гравитационные/летающие враги: подключить PhysicsComponent (сейчас у врага не вызывается), зафиксировать контракт «физика пишет в rect / Enemy владеет _float_x».

### B. Несколько героев и переключение (P1)

- Ввести PlayableCharacter Protocol (общий интерфейс: move/jump/attack/die/get_visual_data).
- Фабрика героев через WorldFactory + HeroConfig.
- Game держит список героев и текущую ссылку, переключение (например по клавише).
- CharacterSelect на уровне.

### C. Платформы: типы и поведение (P1)

- Превратить платформу из голого pygame.Rect в сущность (тип, спрайт, поведение).
- Типы: разрушаемые, движущиеся, шипованные.
- Регистрация через WorldFactory (OCP).

### D. HUD: Theme/Skin-система (P1/P2)

- Вынести цвета/шрифты/раскладку в конфиг theme.json.
- HUD рисуется по теме; сменный внешний вид.
- draw_retro_hud/draw_pixelated_fade получают тему через параметр.

### E. Редактор уровней (P2)

- Генерация готового JSON по стабильной схеме уровня.
- Валидатор в LevelBuilder; редактор и игра на одном языке данных.
- Требует стабилизации JSON-схемы.

### F. Разрушаемые блоки (P2 — идея пользователя)

- OCP-фабрика: register("breakable_block", ...).
- Новое состояние героя AttackState (удар) — после появления атаки у героя.

### G. Инфраструктура качества и автоматизации (P0)

- **G1 (P0)** — **CI/CD пайплайн:** авто-запуск юнит-тестов (см. 4.4) и линтеров на каждый PR, блокировка merge при падении.

## 4. План будущего крупного рефакторинга

### 4.1 Отказ от pygame.Rect в моделях (высокий приоритет в перспективе)

- Собственный dataclass RectPosition в core/geometry.py (без pygame).
- Entity хранит внутренний rect; метод to_pygame_rect() строит pygame.Rect по требованию.
- Затрагивает PhysicsComponent, CollisionSystem, Renderer, CharacterView, Camera, game.py.
- Отдельная итерация + юнит-тесты геометрии и коллизий. Снимает главный блокер масштабирования.

## 5. Конвенции и правила

- Именование: зарезервированные имена (свойства Entity) — только делегаты geometry. Границы зон/патрулей — bound_*/patrol_*. Ключи JSON — snake_case.
- DI: настройки/логгер — через конструкторы, точка создания main.py. Никаких глобалов.
- OCP: новый тип объекта/вью/поведения/состояния — регистрация, не модификация существующих классов.
- EventBus: события только GameEvents.*; подписка токенизированная; ошибки изолируются.
- Тестирование: геометрия/коллизии/позиция — обязательное покрытие перед рефакторингом.
- **Качество кода (доп.):** обязательны линтеры/форматтеры (ruff, black, isort), типизация (mypy/pyright) для новых модулей.
- **CI (доп.):** юнит-тесты и линтеры прогоняются автоматически на каждый PR; merge блокируется при падении.
- **Производительность (доп.):** изменения в моделях/видах не должны деградировать фреймрейт без замера (H1).

## 7. Открытые вопросы и риски

### Риски

1. Зависимость моделей от pygame.Rect — главный блокер масштабирования.
2. Game как God-Object — узкое место при росте режимов.
3. Enemy без физики/гравитации — вертикальные/летающие враги требуют аккуратного подключения.
4. Прямое обращение физики к rect в обход properties — скрытая мина.
5. Отсутствие аудита производительности/фреймрейта — real-time платформер; нет FPS-бюджета, culling камеры, замера render/update.
6. Миграция данных / обратная совместимость JSON-уровней — смена схемы (3.E) может сломать существующие уровни без мигратора (решается в I1).
7. Ввод: input latency / отсутствие rebind клавиш — не описана обработка ввода и настройки управления.
8. Юнит-тесты без CI — без авто-запуска тестов на PR высок риск регрессий (решается в G1).
9. Упаковка/однобинарный запуск/лицензирование Pygame — не описан вариант релиза/дистрибуции.
10. Отсутствие метрик/телеметрии — деградация производительности не отслеживается (решается в H2).
11. Entity как God-класс (9+ зарезервированных properties) — широкий интерфейс, нарушение S/ISP (решается в 4.5).
12. Переусложнение HUD/Theme-системы (3.D) — риск раздувания конфигурации без меры.
